# Current contract: edge platform, security and operations

Baseline: `4187033` (2026-10-23). This specifies checked-in behavior and operational boundaries, not a blanket security, zero-cost or deployed-configuration certification. See [index](README.md), [telemetry/admin](current-telemetry-admin.md), and [platform/content](current-platform.md).

## EDGE-01 — Runtime and binding responsibilities

Astro compiles static documents and assets. Deployment uses **Cloudflare Workers with Static Assets**, not an Astro SSR adapter or a Pages Functions project. [`wrangler.jsonc`](../../wrangler.jsonc) selects [`cloudflare/entrypoint.ts`](../../cloudflare/entrypoint.ts), which exports [`worker.ts`](../../cloudflare/worker.ts). Baseline compatibility date is `2026-09-26`, with `nodejs_compat`; changing it requires separate testing.

| Binding/configuration   | Responsibility                                                                                 | External prerequisites                                                                                                         |
| ----------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `ASSETS` -> `dist`      | Static public delivery and internal authorized admin HTML                                      | Successful SSG build plus vault isolation                                                                                      |
| `DB`                    | D1 visits, quota state, summaries, leads and deployment registry                               | Correct database binding and compatible schema/migrations                                                                      |
| `STORAGE_BUCKET`        | Runtime R2 assets and WAL; helper also recognizes alternate `R2_BUCKET`/`CONTENT_BUCKET` names | Private bucket, correct permissions and lifecycle/capacity management                                                          |
| `AI`, `VECTORIZE_INDEX` | Optional semantic search path                                                                  | Model/index eligibility, vectors, dimensions and usage allowance; binding alone does not populate an index                     |
| `EMAIL` / email handler | Outbound capability binding / inbound Email Routing handler                                    | Account-side email configuration; the inbound handler currently persists and notifies rather than calling the outbound binding |
| Cron triggers           | Two daily schedules invoking the shared rollup/replay handler                                  | Deployed schedules and sufficient runtime/DB/R2 capacity                                                                       |
| Observability           | Logs enabled; tracing enabled at 0.01 head sampling                                            | Account-side access/retention; sampling is not all-request tracing                                                             |

Port/factory interfaces remain in [`src/lib/ports/`](../../src/lib/ports/) and [`factory.ts`](../../src/lib/adapters/factory.ts). Driver keys are `APP_STORAGE_DRIVER`, `APP_SEARCH_DRIVER`, `APP_TELEMETRY_DRIVER`, `APP_CAPTCHA_DRIVER`. Cloudflare-backed factories fall back to local filesystem/S3-compatible storage, static search, SQLite telemetry or honeypot captcha according to actual bindings/driver selection. The main Worker also directly uses Cloudflare primitives; these ports are not a promise of zero-change infrastructure migration.

**Scenario:** Given semantic-search bindings are missing or their call fails/times out, when a search request arrives, then static-memory search remains the fallback instead of blocking public content delivery.

Tests: [`spec-003.test.ts`](../../tests/spec-003/spec-003.test.ts), [`spec-005.test.ts`](../../tests/spec-005/spec-005.test.ts).

## EDGE-02 — Routing, assets, caching and content formats

- `assets.run_worker_first` MUST retain the current `"/*"` interception plus the explicit exclusions: `/_astro/*`, `/fonts/*`, `/remote-assets/*`, `/downloads/*`, `/favicon*`, `/apple-touch-icon*`, `/icon-*`, `/og-default.png`, `/site.webmanifest`, `/robots.txt`, `/sitemap*.xml`, `/llms.txt` (each negative glob in Wrangler).
- Public HTML interception is intentional for initial server-side visits, canonicalization and security. Narrowing interception to `/admin` alone would change that telemetry contract. Static assets served directly through exclusions do not run Worker telemetry.
- `html_handling` is `auto-trailing-slash`, `not_found_handling` is `404-page`. `workers_dev` and `preview_urls` are false in source. Custom-domain declarations cover the apex, admin and blog hosts; account DNS/Access/other vanity aliases are separate resources, not proven by this file.
- The Worker decodes the path once when possible, collapses repeated slashes and strips terminal `.html`. A lowercase comparison copy protects admin/vault matching; public route casing is not globally rewritten by this normalization alone.
- The routing-policy adapter provides permanent trailing-slash `301` document canonicalization and thematic-host `308` redirection with locale/query preservation. These behaviors require the host to reach the Worker; declarations and DNS are not equivalent.
- Public HTML MUST use current ASSETS output without an extra URL-only Cache API HTML cache that can outlive deployments. The response wrapper preserves non-challenge scripts, including ClientRouter, while removing narrowly matched Cloudflare JSD injection. It currently buffers successful HTML to perform that filtering, so a zero-processing/streaming-only claim would be incorrect.
- Fingerprinted assets/fonts use one-year immutable caching. Other image/PDF/index/discovery caching follows [`public/_headers`](../../public/_headers) and the Worker's matching branch; do not claim that `_headers` automatically governs every Worker-generated response.
- `/cdn-assets/<key>` streams a bound storage object or `404`; the R2 adapter uses Cache API absorption before an R2 read and preserves content type/size/ETag. A cache miss still consumes an object read.
- `GET` Markdown negotiation for supported content detail sections uses `.md` or `Accept: text/markdown`, canonical metadata and extracted HTML text, `Vary: Accept`, one-day cache headers and knowledge-base links. It is a generated representation, not the original editorial Markdown source. Search/API/admin noindex behavior and schema rules live in [platform](current-platform.md).

**Scenario:** Given a new deployment with an updated ClientRouter bundle, when a public document is requested, then it is obtained from the versioned ASSETS binding, not an unversioned old document cache. Given an excluded `/_astro/` asset, then it bypasses Worker visit recording.

Evidence: `fetch`, `handleAiMarkdownNegotiation`, `handleCdnStorageAsset`, `handleCachedGet` in [`worker.ts`](../../cloudflare/worker.ts), [`edge-routing-policy.adapter.ts`](../../src/lib/adapters/cloudflare/edge-routing-policy.adapter.ts), [`r2-storage.adapter.ts`](../../src/lib/adapters/cloudflare/r2-storage.adapter.ts). Tests: [`odd-tasks.test.ts`](../../tests/odd-tasks.test.ts), [`spec-005.test.ts`](../../tests/spec-005/spec-005.test.ts), [`seo-aeo-and-db-compaction.test.ts`](../../tests/spec-012/seo-aeo-and-db-compaction.test.ts).

## EDGE-03 — Admin boundary and vault

1. Every external normalized path beginning `/__admin_vault__` MUST return `404`, no-store/noindex, before reading ASSETS, regardless of a caller-supplied internal header.
2. Admin hosts, `/admin` and two-letter localized admin paths, and protected APIs MUST pass `verifyAdminAccess()`. No authenticated-email header, decoded-only JWT, permissive local-dev identity or forged cookie may independently authorize access.
3. Valid Access authentication MUST verify issuer (`https://<team-domain>`), expected audience, numeric unexpired `exp`, matching cached JWKS key and RSA/SHA-256 signature. When an email allowlist is configured it MUST match a normalized allowed email. Production configuration includes both Access settings and require-auth flags; account-side application policy remains independently necessary.
4. The explicitly configured token alternative (`ADMIN_ACCESS_TOKEN`, fallback `ADMIN_API_KEY`, minimum configured length 20) uses SHA-256 digest comparison with bytewise XOR. Accepted transports are Bearer, `X-Admin-Token`, `admin_session` cookie, then query token. Access and configured token are alternative methods, not a requirement to present both.
5. Authentication unconfigured with neither method nor require flag yields `403`; otherwise an unauthorized request yields `401`. Document requests can receive the unauthorized HTML page; APIs receive JSON/challenge headers. No browser-side login state may bypass the Worker.
6. [`isolate-admin-build.mjs`](../../scripts/isolate-admin-build.mjs) moves available generated admin HTML to `dist/__admin_vault__/{default,en,es}/index.html` and removes unvaulted directories. The helper skips absent sources; operators MUST inspect the output when validating a build rather than infer success from a skipped move.
7. Authorized retrieval uses `env.ASSETS.fetch()` internally, selects locale/default fallbacks and applies private no-store/noindex headers. If protected vault output is unavailable, the page returns private `503` rather than an inline dashboard or an unvaulted development copy. Query-token compatibility can create an HttpOnly/Secure/SameSite session cookie; operators SHOULD use verified Access or header-based credentials rather than place secrets into URLs/history/logs. The normal Worker fetch verifies once before entering its private admin dispatcher; direct calls to the exported admin handler still verify independently.

Protected matching includes `/api/admin` and its subpaths, `/api/deployments`, `/api/quota`, `/api/leads` and their subpaths, `/api/metrics`, `/api/telemetry`, `/api/status`, `/status`, and telemetry subpaths except public `POST`/`OPTIONS` collector and `GET`/`OPTIONS` views. Protected preflight returns `204` with configured origin handling but no protected data. The singular `/api/deployment` is a distinct public registry/status route in the current Worker; it MUST NOT be silently described as protected `/api/deployments`.

**Scenario:** Given a forged identity header or `x-admin-vault-internal: 1`, when a client requests a protected API or external vault path, then identity forgery remains unauthorized and the vault path remains `404` without reading private HTML. Given a signed, current, allowed Access JWT, then authorized access remains available.

Tests: [`admin-boundary.test.ts`](../../tests/admin-boundary.test.ts), [`spec-005.test.ts`](../../tests/spec-005/spec-005.test.ts). These source/local cases are not a fresh account-policy or interactive-owner-login audit.

## EDGE-04 — Public APIs, contact and notifications

| Surface                    | Current behavior                                                                                                                                                                                                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/search`              | `q`, `locale` default `en`, `limit` default 8, optional `threshold`; empty query returns empty results. Semantic search races a 350ms fallback through the circuit breaker and returns `{results}`; cache helper adds search tags/TTL.                                                                                                      |
| `POST /api/verify-captcha` | Token verification through selected adapter; 500ms fallback returns unsuccessful verification; success 200, failure 403, invalid request 400. This endpoint's fallback differs from web-contact handling.                                                                                                                                   |
| `POST /api/contact`        | Reads at most 32 KiB of JSON bytes before parsing or rate accounting (`413` for larger declared or streamed bodies without persistence; stream cancellation cannot delay the response), then normalizes locale, limits fields, validates name/email/message, applies anti-abuse gates, persists D1 or falls back to R2 lead WAL, and optionally notifies Discord/Slack/Telegram. Non-POST 405, rate-limited 429 with Retry-After 600, validation/security rejection 400/403, handled success 200; unexpected outer failure 500. |
| Incoming email event       | Applies an application-level 64 KiB declared/streamed raw-message cap (not a Cloudflare platform limit); rejects oversized/unreadable messages, limits stored subject/body to 200/16,384 characters, and schedules the direct D1 insert plus optional notification through `waitUntil()`. A failed insert does not dispatch a success-shaped notification. This separate handler does not implement the web form's WAL/quota logic.                                                                                                                                                 |
| Unknown `/api/*`           | JSON 404/noindex after recognized routes and protected dispatch. Former `POST /api/v1/telemetry` now returns 404 without queuing a write; the active browser collector uses `/api/telemetry/collect`. The historical `edge_telemetry_events` table is not dropped.                                                                                                                                                                                                                                                                            |

Contact inputs are trimmed/truncated: name 100, email 120, phone 35, subject 150, message 4,000 characters; message minimum 20. Some Spanish subject labels normalize to English. Honeypot (`website`/`honeypot`) and supplied `t_sig` under 1.5s silently return success without storing/dispatching. IP limiting is an isolate-memory fixed window of five requests per 10 minutes, not a distributed sliding-window guarantee. Its active-IP table expires entries and caps at 4,096; if all slots are active, a new IP is rejected rather than evicting an active IP's limit. Origin checking uses the actual Worker predicate, not a claim of strict universal origin equality.

When Turnstile is configured, missing token fails validation; explicit `fallback_adblock`/`fallback_network` paths continue with fallback verification status. The contact verification circuit uses a 2,500ms success-shaped timeout fallback, unlike the standalone captcha endpoint. Thus the contact flow is intentionally availability-oriented and MUST NOT be represented as mandatory fail-closed Turnstile on every successful submission. The timeout result can also lead to a verified-status field without a completed upstream check; that field alone is not proof of upstream verification. These are documented existing behaviors, not security approvals or changes.

Web leads at tier 4/missing DB spill to R2; other tiers make one full-schema D1 attempt, then spill to WAL on failure (and trip the quota breaker for recognized quota errors). WAL replay inserts each lead object independently; D1-success/R2-delete-failure can duplicate a lead because the schema lacks a WAL identity. Notification failures are caught separately. Success text or a fallback-selected response is not proof that a lead reached durable storage; no-loss guarantees are unsupported.

**Scenario:** Given a honeypot-filled contact request, when validation reaches that trap, then it returns simulated success without persistence/notification. Given valid required fields but an unavailable persistence sink, then a success response MUST NOT be taken as a durable lead receipt.

Evidence: `handleContactFormSubmission`, `checkContactRateLimit`, `handleCaptchaVerification`, `handleSemanticSearch` in [`worker.ts`](../../cloudflare/worker.ts); [`email-worker.ts`](../../cloudflare/email-worker.ts), [`turnstile-captcha.adapter.ts`](../../src/lib/adapters/cloudflare/turnstile-captcha.adapter.ts). Tests: [`odd-tasks.test.ts`](../../tests/odd-tasks.test.ts), [`spec-003.test.ts`](../../tests/spec-003/spec-003.test.ts), [`spec-005.test.ts`](../../tests/spec-005/spec-005.test.ts).

## EDGE-05 — Headers, repository safety and account controls

HTML responses configure nosniff, DENY framing, strict-origin referrer policy, COOP same-origin, HSTS with includeSubDomains/preload directive, Permissions-Policy, and `Vary: Accept`. A preload header is not evidence of inclusion in browser preload lists. CSP in [`public/_headers`](../../public/_headers) permits the project's selected Cal.com, Turnstile and analytics origins as well as inline/data allowances; it is not a strict nonce-only CSP or proof of injection immunity. Worker-generated API/admin responses use their own explicit headers.

Scanner-path rejection is implemented in source and excludes normal telemetry. Account WAF, Bot Fight/JavaScript Detection settings, DNS, Access policies, email routing and CDN cache rules are **external controls**. Historical IDs or statements in old docs do not prove their current deployment. Client/edge JSD defenses in this repository are not a substitute for inspecting authorized account settings.

Secrets MUST remain outside Git and public build output: admin bearer/API token, Turnstile secret, R2/S3 access secrets, webhook URLs, Telegram bot token, deployment credentials. Public docs use variable names/placeholders only. R2 editorial content, real leads and raw telemetry are not fixtures or public backups. Check staged/history changes before publication; removing a leaked value from HEAD alone does not revoke it or erase external clones/caches. Credential rotation and historical cleanup are separate authorized operations.

**Scenario:** Given an operator updates documentation or verifies a build locally, then no production write, credential discovery, authenticated account probe, content upload, cache purge, database reset or deploy follows implicitly. Each remote mutation requires its own scoped authorization.

## EDGE-07 — Local verification and operational boundaries

The package scripts are authoritative. [`docs/cloudflare-edge.md`](../../docs/cloudflare-edge.md) provides the safe operational reading path; [content guide](../../docs/content-sync.md) describes build-time R2 inputs.

- `pnpm check`, `pnpm test`, `pnpm audit` are local checks. `pnpm build` includes automatic content pull and vault relocation; content hydration/auth prerequisites must be understood before running it.
- `pnpm dev-prod` checks then starts explicitly local Wrangler on port 8788, whose custom build runs static generation/isolation once without content-pull hooks; `--env local --local` uses explicit local D1/R2 and omits remote-only AI/Vectorize and email delivery, retaining production settings separately; this is the appropriate combined static/Worker preview, not proof of production Access/account behavior. `dev-prod` binds to `0.0.0.0` for LAN testing; use a trusted network.
- `db:schema:local` bootstraps tables; upgrades use the tracked migration history appropriate to the existing database. `db:reset:local` drops local data and requires explicit consent/backup planning, not a routine troubleshooting recipe. There is no package alias for remote schema replay or remote reset; remote D1 maintenance still requires separately authorized, backed-up Wrangler operations.
- `content:push`, `cv:publish`, prune, deploy, secret changes, remote DB work and cache/search-index notifications are mutations. No authenticated command is part of this documentation update.
- Wrangler is this repository's runtime/deploy configuration. `cf` can be used for separately authorized account operations/content transports, but `cf dev/build/deploy` is not an interchangeable command for this Wrangler-configured project.
- Restore/rollback planning separates versioned code, private editorial content, D1 records and account configuration. Git rollback does not restore deleted production data, rotate secrets or roll back R2 objects automatically.
